# Personal AI ATC for MSFS 2024 — Build Plan

Owner: Valen. Personal use only. MSFS 2024 (Microsoft Store), SimConnect already available.
Home airports: SABE (Aeroparque Jorge Newbery), SARC (Corrientes). Also any random US airport, set up in 10-15 min.
Latency budget: 3-4 s from end of speech to start of reply audio.

## Decisions so far
- Standalone prototype. No dependency on OpenSquawk's hosted service (invite-based, asks for API keys). Its Bridge app is public (AGPL-3.0) and uses the same `SimConnect` Python package, so it is a useful reference for reading the sim. Check AGPL terms before copying any code.
- SimConnect only: own telemetry plus nearby AI traffic. No LittleNavMap. VATSIM only as the optional Phase 7 helper.
- Voice: Piper (local) first, cloud voice later if needed. English first, then Spanish and Norwegian voices.
- LLM: small fast model through an API key (bought next week). Until then, stub the LLM and use canned replies.
- Airports are generated by a script, then hand-edited. Never written from scratch.

## Architecture

```
mic (push-to-talk) -> STT (faster-whisper) -> prompt builder -> LLM -> TTS (Piper) -> radio filter -> speakers
                                                   ^
        telemetry + nearby AI traffic (SimConnect) + airport file (YAML)
```

Suggested layout:

```
atc/
  main.py            # the loop
  sim/telemetry.py   # own aircraft: pos, alt, speed, heading, com1, squawk, on_ground
  sim/traffic.py     # nearby AI aircraft
  sim/fake.py        # fake telemetry so you can develop without the sim running
  airports/gen.py    # ICAO -> airports/<ICAO>.yaml
  airports/*.yaml    # generated + hand-edited
  llm/prompt.py      # system prompt + context assembly
  llm/client.py      # API call (OpenAI-compatible), stub mode
  audio/ptt.py  audio/stt.py  audio/tts.py  audio/radio_fx.py
```

## Phases

### Phase 0 — Setup (1 evening)
- Python 3.11+ 64-bit (32-bit will not load SimConnect.dll).
- Get the MSFS 2024 SDK SimConnect.dll (SDK installer is in-sim, Developer Mode -> Help -> SDK Installer, as far as I know).
- Install: faster-whisper, piper-tts, sounddevice, pyyaml, an SSE/HTTP client for the LLM.
- Done when: a script prints your aircraft position from the running sim.

### Phase 1 — Telemetry and traffic (1-2 evenings)
- Own aircraft via SimConnect simvars: lat, lon, altitude, ground speed, heading, on-ground flag, COM1 frequency, transponder code.
- Nearby AI aircraft: SimConnect can request data on SimObjects of type aircraft (`SimConnect_RequestDataOnSimObjectType`). Filter to a radius around the airport.
- The Python `SimConnect` package only requests the USER aircraft (its request_data hardcodes the USER type), so AI enumeration uses our own raw ctypes calls (`src/atc/sim/ai_traffic.py`, written, untested). Fallback if that fights you: a Go library for MSFS 2024 exists (Zwergpro/simconnect-go) with AI and facility support, but it means a second language.
- Build `sim/fake.py` at the same time so everything below can be tested with the sim closed.
- Done when: script prints own state plus a list of nearby aircraft (callsign/type if available, position, altitude, on-ground).

### Phase 2 — Airport file generator (1-2 evenings) — the key to the 10-15 min goal
- Input: ICAO code. Output: `airports/<ICAO>.yaml`.
- Data source: OurAirports CSVs (airports, runways, airport-frequencies) as a sim-independent base. Optionally cross-check against SimConnect facility data so it matches what is installed in the sim (addons).
- Generated fields: name, field elevation, runways (ident, heading, length, surface), frequencies (tower, ground, ATIS, approach/departure), towered yes/no.
- Default pattern rules (overridable): US = 1,000 ft AGL, left traffic. Everything else must be filled by hand.
- Hand-edit fields: pattern altitude and direction per runway, preferred runway by wind, local procedures, callsign of the facility, language.
- Done when: `python gen.py KXXX` produces a valid file in under a minute, and you can fix it in a text editor.

### Phase 3 — Voice loop with a stubbed LLM (1-2 evenings)
- Push-to-talk (hold key) -> record -> faster-whisper -> text.
- Text -> Piper voice -> speakers. Choose the voice from the Piper samples page.
- Radio filter: bandpass ~300-3000 Hz, slight noise, short squelch click.
- LLM stubbed with a few canned replies.
- Done when: you say a call, hear an ATC-sounding reply in under ~2 s, without any LLM.

### Phase 4 — Real LLM and system prompt (2-3 evenings, after the API key)
- OpenAI-compatible endpoint (OpenRouter or Anthropic's compatible endpoint). Model: small and fast for normal traffic.
- Prompt assembled each turn: role and phraseology rules, airport file, live state (position, altitude, on ground, frequency), nearby traffic, last few exchanges.
- Rules in the prompt: reply only in ATC phraseology, short, never invent runways, frequencies or traffic that are not in the context, ask for a repeat if unsure.
- Few-shot examples: ground, tower, departure, pattern calls, readback.
- Stream the response to TTS so audio starts as early as possible.
- Done when: a full VFR sequence at SARC works end to end: startup, taxi, takeoff, pattern, landing.

### Phase 5 — Latency and polish (1-2 evenings)
- Measure each stage (STT, LLM, TTS). Target total under 3-4 s.
- Levers: smaller model, shorter prompt, streaming TTS, faster-whisper model size, keep the TTS model loaded.
- Try 3-4 cloud voices against Piper if Piper is not enough.

### Phase 6 — Coverage and languages (ongoing)
- Test at SABE and SARC, then 2-3 random US airports using the generator. Log every wrong reply and fix it in the airport file or the prompt.
- Spanish (Argentine) and Norwegian voices in Piper, plus prompt variants per language.

### Phase 7 — Optional: VATSIM handoff (low priority, only if wanted)
- Idea: when a human VATSIM controller covers your position, the AI stays silent and says "contact X on frequency Y" (optionally sets COM1). When nobody covers you, the AI takes over. SayIntentions does something similar.
- Data: VATSIM's public live data feed (JSON, polled every ~15 s; check the VATSIM developer docs for the current URL and rate limits). Airport positions (DEL/GND/TWR/ATIS) match by callsign prefix; approach and center coverage needs the community boundary data and a point-in-polygon test on your position.
- Advisory only: never transmit AI replies on a frequency a human controller is using. You cannot be connected to VATSIM as a pilot and use the AI on the same frequencies, so this is a "who covers me right now" helper, not a mix of both.
- Valen's stance: if he flies VATSIM he just flies VATSIM, and if he flies AI ATC he flies AI ATC, so this can be skipped or done last.

## Known weak spots
- Pattern sequencing with other traffic depends on how well AI traffic shows up via SimConnect.
- LLM replies can be wrong at times; the airport file and strict prompt are the main defense.
- Some latency per reply is unavoidable.
- Aeroparque procedures in Argentina need manual editing; the generated defaults will not fit.
